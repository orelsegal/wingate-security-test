# Wingate Bug Investigation Skill

## מטרה
חקירת תקלות באפליקציית Wingate בצורה מסודרת, לפני כל עריכת קוד.
הסקיל **אינו עורך קוד** עד שהמשתמש מאשר את תוכנית התיקון.

---

## כלל ברזל

> 🔒 **אין נגיעה בקוד לפני אישור.**
> קודם חוקרים, מבינים, ומציגים תוכנית — רק אחרי אישור מתקנים.

---

## שלב 1 — הגדרת הבעיה

שאל את המשתמש (אם לא ברור):
1. **מה קורה?** — תאר את הבעיה
2. **מה אמור לקרות?** — מה הציפייה
3. **באיזה מסך / תהליך?** — לדוגמה: "לחיצה על שמור בדף הפרופיל"
4. **באיזה תפקיד / משתמש?** — סטודנט / מאמן / מנהל
5. **האם יש הודעת שגיאה?** — מה כתוב בדיוק
6. **מתי התחיל?** — האם אחרי שינוי מסוים

---

## שלב 2 — חקירה ראשונית (קריאה בלבד)

### 2א — לוקאליזציה
1. מצא את ה-component / קובץ הרלוונטי ב-`src/`
2. קרא את הקוד הקשור לתהליך המתואר
3. זהה היכן הבעיה עשויה להתרחש (UI / logic / data / network)

### 2ב — בדיקת logs ושגיאות
- האם יש `console.error` / `try-catch` שנלכדים?
- האם יש TypeScript errors בקובץ?
- האם יש `undefined` / `null` שנגישים בצורה לא בטוחה?

### 2ג — בדיקת תלויות
- האם הקומפוננט תלוי ב-prop שאולי לא מגיע?
- האם יש state race condition?
- האם הבעיה קשורה ל-async / loading state?

### 2ד — בדיקת שינויים אחרונים
- האם הבעיה הופיעה אחרי שינוי ב-routing, auth, Supabase, או component parent?
- אם יש גישה ל-git — בדוק `git log --oneline -5` על הקבצים הרלוונטיים

---

## שלב 3 — סיווג סיכון התיקון

| רמה | תיאור |
|---|---|
| 🟢 נמוך | תיקון בקובץ UI בודד, ללא תלויות חיצוניות |
| 🟡 בינוני | נגיעה ב-hook, state, או לוגיקה משותפת |
| 🔴 גבוה | קשור ל-auth, Supabase, routing, permissions |
| 🚨 קריטי | פוטנציאל לאובדן נתונים / שבירת משתמשים אחרים |

---

## שלב 4 — הצגת תוכנית תיקון (לפני עריכה)

הצג למשתמש:

```
## 🔍 דוח חקירת באג — Wingate

### תיאור הבעיה
[מה דווח]

### ממצאי חקירה
- קובץ רלוונטי: [נתיב]
- שורות חשודות: [X–Y]
- סיבה משוערת: [הסבר]

### סיווג סיכון
🟢 נמוך / 🟡 בינוני / 🔴 גבוה / 🚨 קריטי
סיבה: [למה?]

### תוכנית תיקון מוצעת
1. [שלב 1 — מה לשנות, היכן, למה]
2. [שלב 2 — אם נדרש]

### מה לא לגעת בו
- [אזורים מוגנים הרלוונטיים לתיקון זה]

### אפשרויות
א. ✅ אשר תיקון — אתחיל לעדכן קוד
ב. 🔄 שנה גישה — [הצע אלטרנטיבה]
ג. ⏸️ עצור — המשתמש יטפל בעצמו
```

**המתן לאישור לפני עריכה.**

---

## שלב 5 — תיקון מינימלי בטוח (רק לאחר אישור)

- ערוך **רק מה שהוסכם** בתוכנית
- שינוי מינימלי — לא לנצל הזדמנות "לנקות" קוד נוסף
- אם במהלך התיקון מתגלה בעיה נוספת — **עצור ודווח** לפני שממשיכים
- לאחר תיקון — בדוק TypeScript, ואמת שהלוגיקה הסובבת לא נשברה

---

## שלב 6 — דוח סיום

```
## ✅ דוח תיקון באג — Wingate

### מה תוקן
- [קובץ, שורות, תיאור]

### מה שונה בדיוק
- לפני: [קוד / התנהגות]
- אחרי: [קוד / התנהגות]

### מה לא שונה (ולמה)
- [אם רלוונטי]

### בדיקות מומלצות
- [ ] בדוק את [מסך / תהליך] ידנית
- [ ] בדוק ב-console שאין errors חדשים
- [ ] בדוק תפקידים: סטודנט / מאמן / מנהל

### ⚠️ דגלים פתוחים
- [דברים שנצפו אך לא טופלו — להמשך תשומת לב]
```

## מה אסור לגעת בו (תמיד)

- `src/auth/`, `firebase/`, `supabase/`
- `env`, `.env.*`
- `routes/`, `App.tsx` (routing)
- `package.json`, `bun.lock`
- `vercel.json`, CI/CD
- `CLAUDE.md`
- קבצי schema / migrations / RLS

---

## כללי זהב

1. **לא מנחשים** — רק ממצאים שנצפו בקוד
2. **לא "מנצלים הזדמנות"** — רק מה שהוסכם
3. **לא עורכים ב-auth / db** — אפילו לא אם הבעיה שם — דווח ועצור
4. **מציגים לפני עורכים** — תמיד
